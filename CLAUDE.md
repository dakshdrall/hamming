# Hamming: rules for every session

## What this is
Hamming is a test kit for software that reads the Stellar ledger: a corpus of rare but valid XDR, a replay
harness for indexers, an SDK conformance runner, a Go linter and a hardening guide. It responds to the SCF RFP
"XDR/CAP-Coverage Audit Tool and Indexer-Hardening Guide". License: Apache-2.0.

## Method (mandatory)
1. Verify before implementing. Never state a version, API, field name or CLI flag from memory: read the source,
   run the command, or fetch the docs. Record every fact relied on in docs/FACTS.md (date, value, source).
2. Pre-flight gates: if a required input, pinned commit or tool is missing, STOP and report. Don't substitute
   placeholders or assumptions.
3. verify → implement → self-validate → evidence. Every change ships with a test or a reproducible command
   whose output is shown.
4. Results in results/ are generated by `make` targets only. Never hand-edit a number.

## Commits
- Conventional Commits (feat:, fix:, test:, docs:, ci:, refactor:, chore:). One logical change per commit.
  Every commit builds and its tests pass. The message explains why, not just what.
- No Co-Authored-By lines, no "Generated with" footers, no session URLs.
- Never rewrite published history: no force-push to main, no backdating, no author overrides.
- Work on a branch, open a PR with gh, and let the other teammate review and merge when possible.

## Honesty in data
- Entries derived from core goldens by mutation are synthetic: true, with method and source recorded.
- Persistence is emulated with the target's own encoders unless a real database run is added; say so.
- Don't mention py-stellar-base findings anywhere until the maintainers have the reports.
